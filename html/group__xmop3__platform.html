Sexpr_t Platform_mop3_cell_pool_free ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

THE POOL CELL BLOCKS AND PAYLOADS SHARE. Platform.free-heap is esp_get_free_heap_size() – the AGGREGATE of internal DRAM and PSRAM – which cannot see the pool that actually runs out. cell_pool_free() reports the pool cell blocks are allocated from, and ll_platform_generic.h already names the failure this exposes: the cell heap grows until PSRAM is full and "starves the PAYLOADS (strings, bignum digits, vectors, bytecode) that share that pool".

EXPOSED BECAUSE THE COLLAPSE IS UNINSTRUMENTED. 951 KB can disappear between the last reading and the first alloc_exec failure, with ZERO samples in between – every diagnostic that fires is downstream of the event. A Scheme-visible reading lets bench-timed/run bracket the loss to one benchmark and one phase, which is the one thing none of the existing instrumentation can do.

◆ Platform_mop3_largest_free_dma()

Sexpr_t Platform_mop3_largest_free_dma ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.largest-free-dma) – largest CONTIGUOUS DMA-capable block, in bytes.

WHY THIS EXISTS, AND WHY IT REPLACED A PROBE BUILT ON tone. Measuring whether a board is still USABLE after something has eaten its internal memory needs an instrument with two properties, and a driver's init call has neither:

IT MUST BE REPEATABLE. tone() reaches tone_init(), which creates a FreeRTOS queue ONCE. After the first successful call it can never fail again, whatever the memory state – so an instrument built on it reports "fine" forever. Measured on a classic ESP32: a mass NCG pass drove internal free from 26,532 B to 628 B and the tone probe still reported ZERO failures. A ONE-SHOT INITIALISER CANNOT BE A REPEATABLE PROBE. IT MUST NAME THE RESOURCE THAT ACTUALLY STARVES. DMA-capable is STRICTER than internal, and it is what a camera, an I2S ring or a queue needs. Internal headroom can look adequate while every DMA request refuses.

AND LARGEST, NOT FREE, for the reason ncg_exec_pool_init() already records: free is not the number that decides a CONTIGUOUS request. It once printed INTERNAL free=85448 to explain a refusal whose real blocker was a 14,324-byte largest block. Read this beside Platform.free-dma, never instead of it – the pair distinguishes exhaustion from fragmentation, and they need different fixes.

◆ Platform_mop3_fs_total()

Sexpr_t Platform_mop3_fs_total ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

Filesystem space, in bytes. Platform.fs-total is the size of the mounted filesystem and Platform.fs-used is what is currently occupied; free space is the difference. Both report 0 where no filesystem is mounted, so "no filesystem" is distinguishable from "full filesystem".

WHY AN APPLICATION SHOULD READ THESE BEFORE A SUSTAINED WRITE. Flash write latency is not flat: it rises sharply as the filesystem fills, because the allocator has to work harder to find and erase space. Measured on an ESP32-S3 with a 128-block partition, one chunked file transfer: 76.7 ms per chunk round trip with the filesystem clean, and 1,211 ms per chunk with ~82 KB of other files present – about sixteen times slower, appearing when those files are added and disappearing when they are removed. The writes still succeed and their checksums still match, so nothing fails and nothing warns; a program with a deadline simply starts missing it, and the delay looks like it came from somewhere else entirely.

So a program that must meet a deadline while writing should check free space first and degrade deliberately – write less, write elsewhere, or decline – rather than discover the cost.

◆ Platform_mop3_root_depth()

Sexpr_t Platform_mop3_root_depth ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.root-depth) and (Platform.root-depth-max) – how much of the GC root stack is in use now, and the deepest it has ever been. (Platform.root-depth-max!) re-baselines the peak to the current depth so one piece of work can be measured on its own.

WHAT THE ROOT STACK IS, IN ONE SENTENCE: the runtime records there every heap value it is holding on behalf of code that is mid-execution, so the collector cannot reclaim something still in use. Its capacity is fixed at build time, and exhausting it raises a catchable error rather than corrupting anything – so this pair is a capacity-planning instrument, not a fault detector.

READ THEM AS A PAIR, AND PREFER THE PEAK. The instantaneous depth is whatever happens to be held at the moment you ask, which on an idle REPL is near nothing; it cannot tell you what a workload DID. Two very different programs look identical in a single reading – one that nests procedure calls deeply, and one that iterates a long loop accumulating held values – and they have opposite remedies. The peak distinguishes them: deep nesting is bounded by how far the program recurses, while a loop's peak grows with its ITERATION COUNT, so a peak that scales with the size of the input names a loop.

HOW TO USE IT. Call (Platform.root-depth-max!) immediately before the work and (Platform.root-depth-max) immediately after; the difference is that work's demand. Run it at two input sizes. A figure that stays flat as the input grows is bounded by the program's structure and will stay safe on a larger input; one that doubles when the input doubles will not, and the input size at which it would exhaust the stack is worth computing before a deployment rather than discovering in one.

THE PEAK IS NOT RESET BY A COLLECTION and does not fall when values are released – it is a high-water mark, deliberately, because the number that matters for capacity is the worst moment the program has ever reached and not the comfortable one it is in now.

◆ Platform_mop3_eval_progress()

Sexpr_t Platform_mop3_eval_progress ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.eval-progress) – a monotonic token that advances as the evaluator allocates.

WHAT IT IS FOR. A long computation and a stalled interpreter are indistinguishable from outside the VM: both look like a board that is not answering. From inside they are easy to separate – a long computation keeps allocating and a stalled one does not. Sampling this value, waiting, and sampling again therefore distinguishes SLOW from STOPPED, which no timer can do on its own.

HOW TO USE IT. Compare two samples for equality and nothing else: the value is an opaque token, not a count, and it wraps. Sample it from a timer, a supervisory task or a monitoring loop – never from the computation being watched, which is the thing that may be stuck.

READING IT ALLOCATES, so two consecutive reads differ by a few counts even with nothing in between. Compare the SIZE of a delta against a known-idle baseline, not its mere presence: a delta of a handful means nothing happened, a delta of thousands means work is being done.

◆ Platform_mop3_progress_watch_start()

Sexpr_t Platform_mop3_progress_watch_start ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.progress-watch-start MS) – begin OBSERVING whether the evaluator stalls.

Starts a low-priority sampler that reads the progress token every POLL-MS milliseconds (100 by default, floored at 10) and prints one line if the evaluator has not allocated for MS milliseconds. POLL-MS is the RESOLUTION of the margin that Platform.progress-watch-stats reports, not merely a cost: a gap shorter than one poll cannot be seen at all. It never resets or interrupts anything. Returns #t if a sampler started, #f if one was already running, if the task could not be created, or on a platform where sampling is not provided.

WHAT IT IS FOR. A deadline-driven program cannot tell a long computation from a stuck one by watching the clock, and neither can an operator watching a serial port. This reports the difference: one line, naming how long the evaluator was quiet, with no effect on the program. Leave it running during a long soak and read what the worst legitimate quiet period actually is – that measurement is what makes any later automatic recovery safe to set, and guessing it is how a watchdog ends up restarting healthy work.

MS IS FLOORED AT 100. Below that it measures its own sampling noise rather than the program. A sensible starting point is several times the longest uninterruptible step the application performs; a flash erase or a large allocation can legitimately occupy the evaluator for hundreds of milliseconds.

POLL-MS IS SETTABLE BECAUSE IT IS THE MARGIN'S RESOLUTION, NOT JUST A COST KNOB. The sampler records the gap between allocations only at poll boundaries, so a workload that allocates at least once per poll reports a gap of exactly POLL-MS every time – the FLOOR, indistinguishable from any smaller gap. Measured on an S3 at the 100 ms default: a 19-second allocating workload reported max_quiet_ms=100, i.e. nothing resolvable. To measure the peak rather than the floor, poll faster; the cost is a wakeup per interval and nothing else, since the task reads one word. Floored at 10 ms in ll_progress_watch_start.

< the floor that matters is enforced below; this only stops a negative cast

◆ Platform_mop3_progress_watch_stats()

Sexpr_t Platform_mop3_progress_watch_stats ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.progress-watch-stats) – the MARGIN, as (max-quiet-ms stalls poll-ms), or #f.

Returns #f when no sampler is running, which is deliberately not a list of zeros: a watch that never started and a watch that saw nothing produce the same numbers and mean opposite things.

READ ALL THREE OR NONE. max-quiet-ms is the longest interval the evaluator went without allocating, and it is a MARGIN only while stalls is 0 – the field records the largest gap observed, so a deliberate stall raises it too and would then be reporting the stall back to you. And it is an UNDERESTIMATE by up to poll-ms, because a gap that ends just after a sample is recorded short; the worst true gap is at most max-quiet-ms + poll-ms. A threshold taken from the raw figure is optimistic by that much, in the direction that reboots healthy work.

WHAT IT IS FOR: arm the watch, run the real application for as long as you can stand, then read this. The number it gives is how close your workload came to looking stopped – which is the only honest basis for choosing a threshold that is later allowed to reset the unit.

BUILT BACK TO FRONT WITH EACH PARTIAL LIST PROTECTED. cons() protects its own arguments, but the list being accumulated is a local value not reachable from sexpr, so it needs a root across the next allocation – see the mop3 rule in CLAUDE.md. ONE FRAME, THREE PUSHES, NO POPS. A frame records the rootstack depth on entry and restores it on exit, so each re-push needs no matching pop and the depth cannot drift. The re-push after every assignment is required, not redundant: a push records the VALUE at that instant, and res is a different cell after each cons.

◆ Platform_mop3_progress_watch_arm()

Sexpr_t Platform_mop3_progress_watch_arm ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.progress-watch-arm MS [POLL-MS]) – let a stall RESET the unit.

Until this is called the watch only reports. Armed, a stall of MS milliseconds records the reason wedged, bumps the same death count a declared (dead!) uses – one anti-loop limit, not two – and resets.

THE ACTUATORS ARE LEFT WHERE THE RESET LEAVES THEM. That is a deliberate decision, not an oversight: the mechanism that knows how to stop this machine runs IN the evaluator, and the watch fires precisely when the evaluator cannot run. Of the three ways out – a separate safing task, a board that de-energises on reset, or accepting it – the owner chose to accept it. On a machine that can move, weigh that before arming.

SO ARM IT LATE AND SET MS GENEROUSLY. A false fire costs a reboot with the outputs wherever they were, which is the expensive direction. Measured on an S3: a real workload's worst quiet period is 330-385 ms during STARTUP and 10-30 ms once running, so arming after the application has loaded puts a 1000 ms threshold ~30x away instead of ~2.6x. Read (Platform.progress-watch-stats) on your own workload before choosing.

◆ Platform_mop3_sysmem_inuse()

Sexpr_t Platform_mop3_sysmem_inuse ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(Platform.gc-diag) -> (pass-max-us urgent-max-us urgent-calls). Reported through the RESULT of a mop3 so the bench can display it – warn() output never survives the embedded path (W3_REPL_QUIET at the source, plus serial_run.py dropping any line naming LambMemory or gc_pass), so a warn-based probe silently reports nothing and looks like a clean result. (Platform.sysmem-inuse) -> bytes currently held by the SYSTEM allocator, or -1.

THE CELL POOL CANNOT ANSWER THE FINALIZATION QUESTION, which is why this exists. A vector, bytevector or heap string keeps its ELEMENTS in a malloc'd block and only its handle in a cell – measured: a (make-vector 5000) moved the free-cell count by FIVE. So a backing block that is never freed when its cell is collected is a real leak that every cell-based counter reports as clean. This reads the allocator directly.

-1 means "this build cannot tell", NOT "zero leaked": mallinfo2 is glibc-only, so wasm, MinGW and the ESP32 return -1 and a caller must treat that as UNKNOWN and skip, never as a pass.

◆ Platform_mop3_build_utc()

Sexpr_t Platform_mop3_build_utc ( Lamb & lamb,
Sexpr_t sexpr,
Sexpr_t env_exec )

(lamb-build-utc) -> the compile-time W3_BUILD_UTC of the RUNNING binary.

WHY THIS NEEDS TO BE REACHABLE FROM SCHEME. It is the one value that identifies WHICH BINARY is executing, and until now it existed only in the boot banner – readable solely from a serial transcript, which requires a RESET to capture. That makes it unusable for the thing it is most needed for: confirming an OTA replaced the image, over the network, on a board with no cable attached. Resetting to find out defeats the purpose.

IT IS THE ONE OBSERVABLE NO TOOL IN THE CHAIN CAN FABRICATE. The binary reports its own identity, so a verb cannot claim a successful update by exiting 0 – and several verbs in this toolset have been found doing exactly that. A changed stamp is proof the image changed; an unchanged stamp is proof it did not, whatever anything else reported.

NOTE it dates the BUILD, not the source: a dirty tree produces a binary that is no commit at all (see the header of src/w3_build.h). Use it to answer "is this a different binary than before", which is a question it answers exactly, and never "which commit is this".

◆ ll_feature_names()

const char *const * ll_feature_names ( int * count)

The feature identifiers reported by (features) and matched by cond-expand.

(features) – R7RS (scheme base): the list of feature identifiers this implementation provides (kept consistent with cond-expand).

ONE list, two consumers – see the declaration in ll_platform_generic.h for why.

Only MECHANICALLY DERIVABLE identifiers belong here: the implementation, the platform, the CPU and the byte order, each read from a compile-time macro so it cannot disagree with the binary it is compiled into. A feature that asserts a LANGUAGE property – full-unicode, exact-closed, ratios – is a promise about behaviour and is added only once something tests that the promise holds. Claiming one that is only PARTLY true is worse than omitting it: a program guarding on it takes the wrong branch and says nothing, whereas a missing feature makes it take the conservative branch. full-unicode is the live example – the reader and writer handle every codepoint to U+10FFFF, but char-upcase and friends cover ASCII and Latin-1 only, so the feature is NOT reported.

Platform. LL_WINDOWS and LL_WASM both imply LL_POSIX and then subtract from it, so they are tested FIRST and the posix/unix/linux arm excludes them – see the LL_WINDOWS and LL_WASM commentary in ll_platform_generic.h.

Byte order.
